# Radiarch as a research TPS close to RayStation and Eclipse: evaluation and roadmap

Status: evaluation, 2026-10-20; §4–§6 revised the same day once the direction was set (own the core, engines as subprocess tools, stop vendoring OpenTPS, no calendar deadlines). Inputs: a read-only audit of radiarch (commit `2779c55`, 674 tests passing, 2 skipped), an inventory of the vendored OpenTPS core 3.0.0 and an upstream 2.0.2 checkout, and the public state of matRad 3.2.3, pyRadPlan 0.5.0, PortPy, RayStation v2025 and Eclipse v18. File references are relative to this repository; the audit's paths are as they were on 2026-10-20 (much of what they name has since been replaced).

## 1. Verdict in one paragraph

Radiarch today is a well-structured **proton research planning service** with a mock photon side. The service layer (geometry, beam model, dose, optimization, beam-angle search, evaluation, Celery jobs, Postgres, audit) is sound and tested, and the proton path is real: MCsquare dose and beamlets, robust scenarios, fluence optimization with DVH and gEUD objectives, three solvers, worst-case/expected/CVaR aggregation. But three things a treatment-planning system depends on do not exist or do not work: **photon dose** (the CCC plugin is a stub and the photon plan builder never attaches beams to the plan), **DICOM RT plan objects** (RTPLAN is neither read nor written; RTDOSE is written only on the old `/plans` path and without a frame of reference or referenced plan), and **deliverability** (no linac model, no MLC apertures, no MU calibration, no arcs). A commercial TPS is defined by exactly those three things plus clinical-goal evaluation, plan approval states and a scripting API. The physics itself is not the problem: the two engines radiarch needs are standalone executables driven by files (MCsquare for protons, the WiscPlan collapsed-cone binary for photons), and both are already in the tree. What stands between them and a TPS is the layer in the middle, and that layer is where the decision lies. The path chosen on 2026-10-20 is: **own the core** (data model, DICOM in and out, plan model, optimizer, evaluation, writers), **run the engines as subprocess tools** behind our own drivers, and **stop vendoring OpenTPS** in phases, keeping it as Apache-2.0 reference code to adapt from with attribution. Concretely: fix four defects, wire CCC through our own driver, drive MCsquare directly, replace the thin slice of OpenTPS we still import, then build the three missing pieces (RT object writer, machine model with leaf sequencing, clinical-goal evaluation) and a native photon pencil-beam engine as the independent second engine. That gets radiarch to "commercial-shaped"; VMAT optimization, adaptive replanning and Monte Carlo photon reference dose come after, and clinical use never.

## 2. What "close to commercial" should mean here

The goal is standards fidelity rather than vendor fidelity: radiarch plans are never clinically deliverable, and every artifact carries "not for clinical use". So "close to RayStation and Eclipse" should be read as five concrete properties, and the roadmap below is ordered by them:

1. **Same workflow and the same objects.** Patient model → machine model → beam setup → optimization → dose → evaluation against clinical goals → approval state → export of RTSTRUCT, RTPLAN, RTDOSE, RTIMAGE, treatment records, in a form that a commercial TPS, an OIS, OHIF, 3D Slicer and `dciodvfy` all accept.
2. **Credible physics with a written validation.** Engines whose accuracy is documented on water-phantom, heterogeneous-slab and TG-119-style cases, with a second independent engine for the dose check, the way RayStation pairs collapsed cone with Monte Carlo.
3. **Deliverable-shaped plans.** Control points, MLC leaf positions, jaws, cumulative meterset weights and MU that satisfy a stated machine model (leaf width, leaf speed, gantry speed, dose rate), even though the machine is synthetic.
4. **Evaluation the way a physicist reads it.** DVH, clinical goals with pass/fail and priority, conformity and homogeneity, NTCP/TCP and EQD2, robustness bands, plan comparison and accumulated dose.
5. **Automation.** A scripting SDK and protocol templates that can plan a case end to end without a GUI, which is what ESAPI, RayStation's Python API, RapidPlan and auto-planning amount to in practice.

What it must not mean: a site-tuned beam model matching a real Eclipse or RayStation (impossible without commissioning data), regulatory clearance, or any plan reaching a treatment queue.

### 3.2 Defects that must be fixed before anything else

These are not gaps; they are code that cannot work as written. Each is a day or less.

1. **Photon plans have no beams** *(fixed in R0; R1 replaced the OpenTPS plan with radiarch's own `models/photon_plan.py`)*. `PhotonPlan.beams` returns a copy of the internal list (`src/opentps/core/data/plan/_rtPlan.py:98-100`), so `photon_plan.beams.append(beam)` in `services/photon_beamlets.py:112` and `core/workflows/photon_ccc.py:49` discards the beam. The attribute names used (`gantryAngle`, `segments`, `monitorUnits`, `jawOpeningMM`) are also not OpenTPS's (`gantryAngle_degree`, `appendBeamSegment()`, `mu`, `x_jaw_mm`). The unit tests use fake plan classes with a plain list, which hides this. Consequence: the photon workflow has never produced dose.
2. **Robust proton settings are ignored** *(fixed in R0)*. `core/workflows/proton_robust.py:59-60` sets `setupSystematicErrors`/`setupRandomErrors`; OpenTPS reads the singular names (`_robustness.py:38-39`), so the defaults 1.6/1.4 mm always apply. Paediatric craniospinal plans need ±3 mm / 3.5 %.
3. **The beam model ignores the geometry it was given** *(fixed in R0: `services/geometry_bundle.py`)*. `services/beam_model.py:150` reloads the default data root instead of the `geometry_id` the caller built; `isocenter_mm` enters the cache key but is never passed to OpenTPS. Every beam model is built on the SimpleFantom phantom unless the data root is overridden.
4. **The 4D simulator returned random numbers.** `core/simulator.py` always took the synthetic branch; its OpenTPS branch called methods that do not exist. *Removed on 2026-10-20* together with the `/simulations` endpoint, the synthetic planner fallback (`force_synthetic`; a failed workflow now fails the job with its error) and the OHIF extension (viewing belongs to an OHIF deployment outside radiarch). Suite after removal: 666 passed, 2 skipped.

Also: the "analytic" engine is a deliberately toy model whose Dij columns are all identical (`dose_engines/analytic.py:206-209`), fine for tests but it must never be selectable in a deployment; the old `/plans` workflows load from the data root and ignore `study_instance_uid`; API-key auth covers only four routers (`api/security.py:48-87`); there is no top-level LICENSE and no "not for clinical use" string anywhere in code, docs or UI.

## 4. Engine strategy: own the core, run the engines as tools

The question of the photon engine (OpenTPS is proton-first) splits into two once the vendored code is inspected: which *engines* compute dose, and who owns the *core* between the DICOM objects and those engines. The answers differ.

**What radiarch owns today, and what it still takes from OpenTPS.** The optimizer, beam-angle search, evaluation, API, job system, persistence and audit are radiarch code with no OpenTPS inside. The slice still imported is thin, 17 modules: DICOM loading (`dataLoader`), the CT, ROI and plan data classes, proton spot placement (`ProtonPlanDesign`), CT calibration tables, and the MCsquare and CCC wrappers (`mcsquareDoseCalculator.py` 1,259 lines, `mcsquareIO.py` 1,097, `CCCdoseEngineIO.py` 269). That slice is where the defects of §3.2 came from (the plan-model attribute mismatch, the ignored robustness names), it carries the broken DICOM writers, and it is what forces a dependency change on every upstream release: 3.0.1 required numpy 2, scikit-image and nibabel in the core, not the GUI. pyRadPlan is worse on that axis (below).

**Decision, 2026-10-20: the core is radiarch's own code; OpenTPS is reference code, not a dependency.** OpenTPS core is Apache-2.0, so its IO and spot-placement code can be adapted with attribution wherever that is faster than writing from scratch. The replacement is phased: the vendored 3.0.1 copy stays in the tree (reproducibly, through `scripts/vendor-opentps.sh` and `src/opentps/patches/`) until each piece has its own implementation and the regression test passes. That test is strong because the engine binary and its inputs do not change, so dose and beamlets must come out identical. The pieces and their estimates: a CCC file driver, 3–4 days (needed for R1 under any option); an MCsquare driver, about one week and 600–900 lines (config writer, CT to MHD, plan text, BDL and scanner paths, MHD dose and sparse-beamlet readers; the pre-OpenTPS standalone interface kept under `tests/opentps/core/MCsquare-python_interface/` shows the whole thing was done without OpenTPS before); DICOM CT and RTSTRUCT loading with pydicom and SimpleITK, 3 days; contour rasterization, 1 day; proton spot placement, about 4 days (roughly 400 lines of energy-layer and raster logic); CT calibration table parsing, 1–2 days; retiring the legacy `/plans` workflows that call OpenTPS's optimizer, which the services already replace. Three to four weeks in all. At the end `src/opentps` is deleted and an `engines/` directory keeps the binaries, data and licences, with today's vendoring script turned into an engine-fetch script. What we give up is OpenTPS's wrapper-level extras (its 4D delivery simulation, `RobustnessEval`, Morphons registration); 4D and scenarios are MCsquare-native, and registration comes from SimpleITK.

**MCsquare directly (Apache-2.0).** MCsquare is a standalone binary driven entirely by files: a text config, the CT as MHD plus HU→density and HU→material tables, a plan text file, a beam data library and a scanner directory. Its config already exposes everything radiarch uses through OpenTPS: `Beamlet_Mode` with `Dose_Sparse_Output` for the Dij, `Scenario_selection` (All, Random) with `Num_Random_Scenarios` for robustness, `4D_Mode`, LET output, `Compute_DVH`, `Dose_to_Water_conversion` and a `Stat_uncertainty` target (`tests/opentps/core/MCsquare-python_interface/Process/ConfigTemplate.txt`). There is no PyPI package for MCsquare alone; the source is on GitLab and the binaries radiarch has (156 MB: five CPU variants and `libMCsquare.so`, 84 materials, two IBA double-Gaussian BDLs, the UCL_Toshiba scanner) came through OpenTPS 3.0.1. They become a pinned engine asset with recorded provenance, licence and rebuild-from-source instructions.

**CCC, the WiscPlan collapsed-cone binary (GPLv2).** The interim nominal photon engine, behind our own driver. It is real: a Linux x86-64 binary run over files (kernels directory, HU tables, a geometry file, a beamlet list; the protocol is visible in `CCCdoseEngineIO.py`), with beamlet computation and robust scenarios in shift and simulation modes. Its limits: generic 6 MV kernels only, no linac head model (no output factors, head scatter, MLC transmission or tongue-and-groove), no absolute MU calibration, no published validation, no Windows or macOS binary. Collapsed cone handles lateral scatter in lung better than pencil beam does, which is why it carries the nominal photon dose until the validation harness (R7) says otherwise. Because it is a separate program invoked over files, the GPLv2 term stays confined to that program; radiarch never links or imports it and says so in NOTICE.

**pyRadPlan 0.5.0 (DKFZ, September 2026).** Pure Python, no MATLAB (the `matlabengine` and `oct2py` extras are optional; "matRad-interoperable" means it reads matRad's data files). It ships matRad's SVD photon pencil beam with a generic linac base-data set, runs on NumPy, CuPy, PyTorch or JAX, optimizes with SciPy or IPOPT, and reads and writes CT, RTSTRUCT, SEG and RTDOSE ([changelog](https://github.com/e0404/pyRadPlan/blob/main/CHANGELOG.md)). It has no VMAT, no aperture optimization, no leaf sequencing and no RTPLAN export. Its core requires `pydantic_ai`, `huggingface_hub`, `safetensors`, `pint`, `h5py`, `pymatreader` and array-API shims, and pins `numpy<2.4` and `pydantic<2.20` ([pyproject](https://github.com/e0404/pyRadPlan/blob/main/pyproject.toml)); it is pre-1.0 and its API moves. **Not a runtime dependency.** Use it offline, in its own environment, as a cross-check engine for the validation harness. Its generic photon base data is matRad's `photons_Generic.mat`, which is GPL v3 like the rest of matRad; the native engine below must therefore take its beam data from a permissively licensed or self-generated source (published representative beam data, or an OpenGATE Monte Carlo run of our own), not from that file.

**A radiarch-native photon pencil-beam engine.** What a second engine needs is `compute_dose` and `build_influence` behind the five-method `DoseEngine` protocol. A finite-size pencil-beam engine with radiological-depth heterogeneity correction (the matRad/pyRadPlan SVD design) is two to three weeks including a CuPy path, has no new dependencies, and is fast enough for VMAT-scale Dij. Its accuracy is pencil-beam class (5–10 % low in lung), acceptable for optimization and for the secondary check once the nominal dose comes from CCC. A native collapsed-cone engine would be four to six weeks and needs polyenergetic point kernels (the WiscPlan kernels are GPLv2; computing our own with OpenGATE is a few days of compute); decide after R7. Monte Carlo should be integrated, never written. In every case the real cost is validation, not code: the harness in R7 is needed whichever engine is chosen and is reusable for all of them.

**matRad 3.2.3 (GPL v3, MATLAB/Octave; corrected 2026-10-21 — an earlier draft said BSD-3).** Not a runtime engine; a MATLAB or Octave process behind a Python service is a maintenance liability. Use it as an offline cross-check (its pencil beam and ompMC Monte Carlo on the same TG-119 phantoms) and as the reference implementation to port the **Siochi leaf sequencer and direct aperture optimization** from (`matRad_example3_photonsDAO.m`), the shortest path to deliverable step-and-shoot plans ([releases](https://github.com/e0404/matRad/releases)).

**Monte Carlo photon reference.** Commercial TPSs validate collapsed cone against Monte Carlo, and lung dose needs Monte Carlo or Acuros-class accuracy. Radiarch needs an MC engine for the validation report, not in the planning loop. Options, both subprocess-isolated: ompMC (EGSnrc physics, OpenMP, GPLv3, the engine matRad uses) or OpenGATE 10 (Geant4, Python, slow but a gold standard).

**PortPy.** Not a dependency: its influence matrices come from Eclipse and its licence carries a non-commercial clause. Its sequential-convex-programming VMAT formulation is a good reference when R8 is designed ([PortPy](https://github.com/PortPy-Project/PortPy)).

Summary of roles: own core; MCsquare for protons and CCC for nominal photon dose, both as subprocess tools behind our own drivers; a radiarch-native pencil-beam engine as the second runtime engine and the fast Dij for optimization; an MC engine for validation only; pyRadPlan (BSD-3) and matRad (GPL v3) as offline cross-checks and algorithm sources; OpenTPS as Apache-2.0 reference code until it is gone from the tree.

## 6. Decisions

Recorded on 2026-10-20:

1. **Core and engines:** the core (data model, DICOM in and out, plan model, optimizer, evaluation, writers) is radiarch's own code. Engines are standalone executables run as subprocess tools behind radiarch drivers: MCsquare for protons, the WiscPlan CCC binary for nominal photon dose, Monte Carlo (ompMC or OpenGATE) for validation only. A radiarch-native photon pencil-beam engine is the second runtime engine. pyRadPlan and matRad are offline cross-checks and algorithm sources, never runtime dependencies.
2. **OpenTPS is not a dependency.** Vendoring stops. The 3.0.1 copy stays in the tree, reproducibly, until each imported piece has its own implementation (R1, R14, R2, R15), then `src/opentps` is deleted and only engine binaries, data and licences remain under `engines/`. OpenTPS code is adapted where useful under Apache-2.0 with attribution.
3. **Writer location:** the RT object writer lives in radiarch as pydicom code, not on the OpenTPS writers, which omit MLC and have crash-level bugs.
4. **Deliverability target:** step-and-shoot IMRT with a synthetic 120-leaf machine first, VMAT immediately after (R8); the order is unchanged by the engine decision, only the dates are gone.
5. **Schedule:** the work is sequenced by the "Order" column in §5, not by calendar dates.
6. **Retired fiction (done):** `/simulations`, the synthetic planner fallback and the OHIF extension were removed on 2026-10-20; nothing in the service can return invented numbers.
7. **Housekeeping (done):** the old 2.0.2 OpenTPS checkout was replaced with a 3.0.1 clone; radiarch vendored 3.0.1 through `scripts/vendor-opentps.sh` with a tracked patch set, on numpy 2 (until R15 removed it).

Still open:

- **MCsquare binary provenance:** keep the binaries that came through OpenTPS 3.0.1 or rebuild from the MCsquare GitLab source at a tagged version (settle in R14; rebuilding also gives an AVX-512 build for the workstation).
- **pydicom 3 migration:** scheduled inside R15; the writers (R6) should be written against pydicom 3 from the start.
- **Native collapsed cone:** only if R7 shows CCC's generic kernels or missing head model limit the lung plans; otherwise CCC stays.
